1. PROJECT OVERVIEW
================================================================================
QR Studio is a responsive, web-based QR Code generation and management system
built with Python (Flask) and modern client-side JavaScript. 

Unlike basic generator utilities, QR Studio features:
  - Real-time debounced preview generation.
  - Server-side pixel-perfect rasterization with error correction.
  - Automatic contrast ratio analysis using WCAG 2.1 formulas.
  - An embedded SQLite persistence layer with deduplication and bounded FIFO history.
  - Dual retro-aesthetic themes (CRT Terminal and Windows 98) managed via HTTP cookies.
  - Robust input sanitization and DoS protections.

3. SYSTEM ARCHITECTURE & COMPONENTS
================================================================================

1. BACKEND (Python / Flask)
   - app.py: Core application routing, business logic, validation, image
     rasterization, and database interactions.
   - Built on Flask's WSGI micro-framework, running without external daemon
     dependencies.

2. QR ENGINE & IMAGE PROCESSING (qrcode + Pillow)
   - qrcode library generates the matrix modules.
   - Pillow (PIL) scales the modules sharply using nearest-neighbor sampling,
     avoiding blurry anti-aliasing artifacts, and centers the code onto a
     custom-colored square background canvas.

3. PERSISTENCE LAYER (SQLite3)
   - File-based database: instance/qr_studio.db.
   - Automatically initializes table schemas and descending chronological indexes.
   - Implements FIFO self-cleaning: caps history to the 50 most recent records.

4. FRONTEND (Vanilla HTML5 / CSS3 / ES6 JS)
   - No heavy frameworks (React/Vue/Webpack) - instant page loads and zero compile step.
   - CSS variables power two retro themes:
       * Terminal: Phosphor-green monochromatic CRT appearance.
       * Win98: Classic beveled grey UI window chrome.
   - Asynchronous Fetch API for frictionless generation without full-page reloads.

================================================================================
4. STEP-BY-STEP DATA LIFECYCLE
================================================================================

1. INPUT: User types a URL or string and modifies color pickers / size slider.
2. CLIENT-SIDE ANALYSIS:
   - Client calculates relative luminance: Y = 0.2126R + 0.7152G + 0.0722B.
   - If contrast ratio < 3.0, displays a real-time warning.
3. DEBOUNCED DISPATCH:
   - Waits 500ms after last text keystroke (or 250ms for slider) to avoid spamming.
   - Attaches an incrementing `sequence` counter to discard out-of-order network responses.
4. SERVER VALIDATION:
   - `parse_payload()` checks character counts, valid hex color patterns, and URL protocols.
5. GENERATION:
   - `render_qr_png()` constructs the matrix with 15% error correction (Level M),
     resizes via `Image.NEAREST`, centers onto canvas, and writes to `io.BytesIO`.
6. DATABASE SYNC:
   - Checks if this exact QR configuration already exists.
   - Updates timestamp if found, or inserts new record and deletes records older
     than top 50.
7. CLIENT PRESENTATION:
   - Base64 payload renders immediately in the preview stage.
   - Download link (/download/<id>) is populated.

5. SECURITY & OPTIMIZATION IMPLEMENTATIONS
================================================================================

1. DoS PREVENTIONS:
   - `app.config["MAX_CONTENT_LENGTH"] = 128 * 1024` (128 KB hard payload ceiling).
   - Character count clamped to 1000 characters for content, 80 for labels.
   - Image size range clamped between 100px and 600px.

2. PROTOCOL INJECTION / SSRF DEFENSE:
   - URLs must strictly begin with `http://` or `https://` with a non-empty
     network location (netloc). Rejects `javascript:`, `data:`, or `file://`.

3. SQL INJECTION IMMUNITY:
   - All queries in `app.py` use parameterized placeholders (`?`), preventing
     user input from altering SQL statements.

4. RACE CONDITION HANDLING:
   - Client-side sequence tracking ensures slow previous requests don't overwrite
     more recent keystrokes if they arrive late.

5. CACHING & MEMORY MANAGEMENT:
   - PNG images for history items (`/qr/<id>.png`) are generated dynamically on demand
     and served with `max_age=300` HTTP headers to utilize browser cache.
   - Database stores parameters rather than large image blobs to keep DB file tiny.

6. CROSS-QUESTIONING & VIVA DEFENSE GUIDE (Q&A)
================================================================================

Q1: Why did you choose Server-Side Generation over Client-Side JavaScript libraries?
A1: Server-side generation guarantees centralized data integrity and permanent
    download links (/download/<id>). It also enables high-fidelity image rendering
    using Pillow's integer scaling without client device rendering variations.

Q2: Why did you choose SQLite over MySQL or PostgreSQL?
A2: SQLite is a self-contained, serverless, zero-configuration ACID database.
    Since this project maintains a bounded 50-item history per instance without
    complex distributed clustering needs, SQLite delivers sub-millisecond
    performance with zero background infrastructure overhead.

Q3: What error correction level did you use in QR generation and why?
A3: We chose `ERROR_CORRECT_M` (Level M), which provides approximately 15% error
    recovery capability. It balances scan reliability (handles small smudges/scratches)
    without overly increasing module grid density like Level Q (25%) or H (30%) would.

Q4: How do you prevent blurry or fuzzy edges on scaled QR codes?
A4: Blurry edges happen when bilinear or bicubic interpolation resizes high-contrast
    grids. We calculate the integer multiple factor:
        box = max(1, size // modules.width)
    and use `Image.NEAREST` resampling. This preserves mathematical sharpness on
    every individual QR module.

Q5: How does the system handle fast typing without choking the backend?
A5: We implement client-side debouncing (delaying fetch by 250-500ms after the last
    event). Additionally, a monotonic sequence counter (`state.sequence`) drops
    stale network responses that arrive out of order.

Q6: How does the WCAG contrast calculation work?
A6: The client converts hex colors to normalized sRGB color channels, converts them
    to linear luminance values, and applies the standard WCAG formula:
        (L1 + 0.05) / (L2 + 0.05)
    If the contrast ratio is under 3.0, it flags the code as low contrast.

Q7: What protects the system against storage exhaustion?
A7: The database runs an automated subquery prune after each insert:
        DELETE FROM qr_codes WHERE id NOT IN (
            SELECT id FROM qr_codes ORDER BY created_at DESC, id DESC LIMIT 50
        )
    This enforces a fixed storage ceiling.

Q8: How does theme persistence work across reloads?
A8: When switching themes, an HTTP POST to `/settings` sets a cookie with
    `max_age=31536000` (1 year) and `SameSite=Lax`. Flask's `@app.context_processor`
    reads this cookie and injects the active theme attribute into the `<html>` root.
